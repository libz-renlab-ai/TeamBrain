# PR #254 fix-plan — `/review` iter-2 finding

PR: https://github.com/libz-renlab-ai/TeamBrain/pull/254
Iter: 2 of `/review` loop on `feat/issue-244` (driven by `/fixed-flow-driver` + local `/review` skill, not the cloud Codex bot per ADR-0007).

## ① Task description

**做什么**：修复 `packages/cli/src/lib/update-state-lock.ts` 里 `tryStealStaleLock` 的 TOCTOU race window。

**为什么**：`acquireLock` 用两条 syscall 建立 lock 文件 —

```ts
const fd = fs.openSync(lockPath, "wx");      // L94: 创空文件 (atomic, EEXIST if held)
fs.writeSync(fd, String(process.pid));       // L95: 写 pid 进去
```

Between L94 and L95（数纳秒到几微秒），文件存在但内容为空。一个并发 caller 撞进这个窗口会走到 `tryStealStaleLock`：

```ts
const raw = fs.readFileSync(lockPath, "utf-8"); // 读到 ""
const pid = parseInt(raw.trim(), 10);            // NaN
if (!Number.isFinite(pid) || pid <= 0) {
  fs.unlinkSync(lockPath);                       // 删掉 holder 的锁
  return tryCreateLock(lockPath);                // 自己创新锁
}
```

→ 两个 caller 都自认为持锁、并发跑 mutator。这正是 #244 要消灭的 lost-update 场景，从锁的内部又泄回来了。

**怎么改**：把 `tryStealStaleLock` 里 "garbage, treat as stale" 那条路径直接 `return false`，不再 unlink + steal。让外层 retry 在 `acquireLock` 的下一轮再读 —— 那时候原 holder 已经写完 pid，stale-pid 检测能正常工作。如果是真垃圾（极少数 partial-write），最坏 case 走 5 次重试后 fall through 到 non-locked write，与 helper 现有 fail-open 语义一致。

**不做什么**：
- 不改 `acquireLock` 的两段式 create+write（用 `link()` 重写也行，但范围更大；上面 1-line 改动已经够）。
- 不动 `commands/update.ts:writeState` 的 passthrough mutator（PR diff 里有 explicit comment 说"foreground intent should win"，是 design choice，不是 bug；residual 影响仅是偶发"提前一次更新检查"）。
