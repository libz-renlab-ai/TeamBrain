## ① Task description

### What

Fix three bugs in `apps/landing/lighthouserc.json` (introduced in commit `fa92538` of PR #178) and add a `.gitignore` entry for the run artifacts:

1. **P1** (lines 12–14): Lighthouse CI category assertions use bare names (`performance`, `accessibility`, `seo`) instead of LHCI 0.13's required `categories:` prefix. Each `lhci autorun` aborts with `"X is not a known audit"` before any scoring runs. This silently breaks `pnpm --filter @teamagent/landing verify` — the gate that issue #120's acceptance criteria depend on.
2. **P2** (line 15): Issue #120 acceptance is `LCP ≤ 2.5s`, but the config only enforces FCP. FCP correlates with LCP but they measure different things.
3. **P3** (`.gitignore`): `apps/landing/.lighthouseci/` not ignored. Each `verify` run produces `lhr-{epoch}.{json,html}` + `assertion-results.json` artifacts that are regenerated, not source.

### How

- Edit `apps/landing/lighthouserc.json`:
  - `"performance"` → `"categories:performance"`
  - `"accessibility"` → `"categories:accessibility"`
  - `"seo"` → `"categories:seo"`
  - Add `"largest-contentful-paint": ["error", { "maxNumericValue": 2500 }]` line
- Edit `.gitignore`: add `apps/landing/.lighthouseci/` after the existing `# CLAUDE.md compile-hook ...` block.

### What NOT to do (anti-goals)

- Do NOT touch `docs/plans/issue-120/{plan,research,judge}.md` — they're correct as shipped.
- Do NOT remove the FCP assertion — it's still useful as a tighter early-paint guard.
- Do NOT introduce new categories or audits beyond what issue #120 specifies.
- Do NOT rebase or force-push PR #178 — push fix commits on top.
- Do NOT close PR #179 — it's the dependent implementation PR, will rebase cleanly once #178 merges.
- Do NOT punt this to a follow-up issue (`POSTPR` hard rule).
