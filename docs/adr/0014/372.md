# 1. 最大产品问题：我们到底在服务谁？

## Grill 问题

TeamBrain 是给 individual developer 自己用，还是给 team lead 管理团队进展用？

## 可选答案

A. 只做 developer-local memory / hook 工具
B. 只做 leader 监控平台
C. developer 工具为底，leader dashboard 为上层产品
D. 两条产品线完全分开
E. 暂不决定，先做底层 hook

## 裁决

选 **C**，但产品叙事上优先说：

> **TeamBrain 是给 team lead 用的 AI work observability platform。**

底层还是 developer agent / hook / audio / statusline，但第一商业价值要落在 leader：

```txt
leader 不用问人，也能知道：
  谁现在在推进？
  哪个项目有风险？
  哪个人 / 哪个 issue 卡住了？
  今天每个成员在每个项目上做了什么？
```

原因是 #309 明确不是在问“做一个漂亮 UI”这么简单，它说“等前端去做个花里胡哨的界面，然后我们再给界面补后端”，这其实是在逼问 app 怎么证明自己能给小 B leader 提效。citeturn138076view5

所以首页不能先放配置中心，也不能先放 statusline 美化。首页必须证明三件事：

```txt
1. 当前谁 / 哪个项目正在动？
   -> #308 green light

2. 哪里异常，需要 leader 介入？
   -> #372 live inspection / incident

3. 今天做了什么？
   -> #371 member × project daily summary
```

# 7. #372 异常状态：不是后台永远重度采集，而是 leader 点击后 live inspection

## Grill 问题

#372 要不要一直后台计算所有成员所有项目的异常？

## 可选答案

A. 是，所有项目持续重算
B. 否，只点开时查
C. #308 green light 常驻，#372 点击后深入收集
D. 只做日报，不做实时
E. 只做 GitHub，不看 AI events

## 裁决

选 **C**。

#372 的需求是 leader 需要知道项目成员的异常状态，并对项目整体作用有完整认知；这不等于每秒后台重算所有成员的所有 GitHub 和 prompt。citeturn138076view10

正确模型：

```txt
首页常驻：
  #308 green light
  low-cost presence

leader 点击成员 / 项目 / green light：
  启动 live inspection session
  拉最近 GitHub activity
  拉相关 #308 AI events
  关联 work item
  生成 progress / abnormal summary

发现异常：
  冻结成 incident record

未发现异常：
  session 结束后只保留必要 telemetry
```

默认窗口：

```txt
点击成员：
  最近 24 小时

点击项目：
  最近 7 天

点击 issue / PR：
  从 issue / PR 创建时间开始

点击 green light：
  当前 session + 最近 24 小时
```

# 8. 异常检测的第一条规则：高 AI activity + 低 GitHub progress

## Grill 问题

什么叫“卡住”？

## 可选答案

A. prompt 次数多
B. GitHub 长时间无更新
C. AI 活跃很高，但 GitHub 没有进展
D. leader 手动标记
E. C 为默认，leader 可配置阈值

## 裁决

选 **E**。

默认 stuck detector：

```txt
if ai_prompt_count >= 5
and github_progress_events == 0
within 60 minutes
then severity = warning

if ai_prompt_count >= 10
and github_progress_events == 0
within 120 minutes
then severity = critical
```

GitHub progress events：

```txt
commit
pr_opened
pr_updated
issue_comment
review_submitted
branch_pushed
status_changed
```

这符合 #372 的“异常状态”，也符合 #308 只是 AI event source 的边界。citeturn138076view10turn138076view4

# 10. identity / project binding：不能靠猜

## Grill 问题

怎么把 GitHub activity 和 AI session 对到同一个人 / 项目？

## 可选答案

A. GitHub username
B. email
C. member_id ↔ github_login ↔ agent_install_id 显式绑定
D. commit author 自动猜
E. 不绑定，日报和异常各算各的

## 裁决

选 **C**。

```txt
member binding:
  member_id
  github_login
  agent_install_id
  team_id
  display_name

project binding:
  project_id
  github_org
  github_repo
  issue_scope
  branch_scope
  leader_ids
```

否则会出现：

```txt
GitHub 上 Alice 提了 PR
AI event 里是本机 user emily
日报不知道是不是同一个人

Claude session 在 repo A
GitHub commit 在 repo B
异常分析不知道属于哪个项目
```

#371 的“多个并行项目”天然要求跨 repo / project 绑定，#372 的异常分析也要求能从 AI event 追到项目上下文。citeturn138076view9turn138076view10

# 21. #310：手机 Web/PWA 一键录音，而不是只修 CLI

## Grill 问题

“不需要开电脑，随时开录”怎么实现？

## 可选答案

A. 只做 CLI
B. 只做移动 app
C. CLI + 手机 Web/PWA 共用 Audio Event API
D. 做 Slack/飞书 bot 上传
E. 先只改文档

## 裁决

选 **C**。

#310 的需求只有一句：“不需要开电脑，随时开录”。这意味着 CLI-only 不够。citeturn138076view6

架构：

```txt
Desktop:
  teamagent audio start/stop/import

Mobile:
  PWA 一键录音
  background chunk upload
  offline local cache
  retry/resume

Backend:
  Audio Event API
  transcription job
  summary job
  plugin dispatch
```

手机录音归属：

```txt
从项目页录音：
  直接挂 project

从全局快捷入口录音：
  先进 personal audio inbox

AI 自动归类：
  只建议 project/issue/PR
  不自动强绑定
```

避免 AI 错归类污染 #371 日报和 #372 异常。

# 22. #320：它不是产品设计主线，是 evidence / coding discipline

## Grill 问题

#320 要不要决定 #308/#371/#372 的产品设计？

## 可选答案

A. 要，所有功能必须围绕 #320 设计
B. 不要，#320 只是文档
C. #320 是 business feature 证明体系，不反向决定产品主线
D. #320 应该延期
E. #320 应该删除

## 裁决

选 **C**。

你前面纠正得对：#320 是 coding/detail/evidence 线，不是 leader 产品设计主线。

#320 要求一个 probe 返回三大 business feature 和四层证据 verdict：CEO / Coder / Machine-readable / LLM-readable raw；它还提到 `docs/BUSINESS-FEATURES.md`、README 三大业务特性、`CLAUDE.md`/`AGENTS.md` canned-answer rule、grep anchors、CHANGELOG 等。citeturn148789view4

它应该给每个业务功能提供证明：

```txt
CEO:
  这个功能解决什么业务问题

Coder:
  哪些文件 / hooks / commands / routes 实现它

Machine-readable:
  JSON / SQL / CLI --json / DB schema 能证明它

LLM-readable raw:
  docs / logs / raw artifacts / canned answer anchors
```

但它不能反过来规定：

```txt
#308 必须怎么设计
#371 必须从 prompt 生成
#372 必须实时后台采集
```

#320 的位置是：

```txt
after design:
  add evidence anchors
  add canned answer
  add docs
  add --json / grep anchors
```

不是：

```txt
before design:
  force product shape
```
