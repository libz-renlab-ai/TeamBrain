## 1. 「主 coding agent 不得在 repo 内新增/修改/提交测试文件」 ⊥ TDD + 契约测试

**Q**: policy §1.1 + §2.1 禁止主 agent 新增 `test_*` / `*_test.*` / `*.test.*` / `*.spec.*` / fixtures / snapshots / 测试配置。这等于说 `/fixed-flow-driver` 不能写 `packages/cli/src/__tests__/*.test.ts`。

**Conflict**:
- `CLAUDE.md` 元约束:「**新增 Port 必须先写契约测试再写实现**。契约测试套件放 `packages/ports/src/__tests__/*-contract.ts`」;
- `CLAUDE.md` 开发节奏:「**TDD**:每个新功能先写测试(看到红)→ 写最小实现(变绿)→ commit」;
- `docs/adr/0010-bottom-level-fixtures.md`(scenario fixture corpus)整套就是 in-repo 的 `tests/fixtures/scenarios/<feature-slug>--<scenario-name>/` 录像档案,**显式**进 main repo,走三层 replay tier(byte / sequence+DB / LLM-judge),α-strict gate;
- `packages/*/src/__tests__/` 目录在所有 7 个 packages 里都已被 vitest 配置 + CI 锁定。

**Recommendation**:
重新定义 policy §1.1 / §2.1 的「测试」为**两类**,只禁后一类:

| 类别 | 写谁 | 何时进 repo | 例 |
|------|------|-------------|-----|
| **contract / fixture / regression(allowed in repo)** | 人或外部 plan 提前规定的、与本次 fix 无关的、TDD red-green-refactor 链路里的「先写测试」 | 一直在 repo | `packages/ports/src/__tests__/*-contract.ts`、`tests/fixtures/scenarios/<slug>/` |
| **self-witness ad-hoc(forbidden in repo)** | 主 agent 在本次 PR 期间为了「证明自己 fix 正确」临时写的 throwaway 验证脚本 | 永不进 repo,落 `/tmp` 或 `.fixedflow/` 临时目录 | 一次性 repro 脚本、临时 mock 服务 |

具体规则:
1. 如果 fix 的 acceptance criteria 已经体现在 issue body / grill comment / PR-PLAN(`docs/PR-PLAN.md`),那对应的 **contract test / scenario fixture** 是计划产物的一部分,允许 commit 进 repo,且**应当**由 driver 写,这就是 TDD red-green-refactor;
2. 主 agent **不得**为「让我自己安心」而临时新增 `*.test.ts` 然后 commit,这类要写也只能落 `/tmp`,不能 git add。

## 2. 「Blind verification subagent」⊥ ADR-0004 既有定义

**Q**: policy §1.2 引入「blind verification subagent」名字,定义其职责为独立攻击主 agent 的 patch、生成 `/tmp` 临时测试、保留秘密回归集。

**Conflict**:
- `docs/CONTEXT.md` L93-95 已经定义了一个 TeamBrain canonical 概念叫 **Calibration subagent**:「Claude Code 用 Agent tool 派出的、专门做 tier 重判的临时 agent。读 events / 搜 gbrain / 看 repo,最后调 `teamagent set-tier` 写回。**不在 TeamBrain 进程里跑**——TeamBrain 不内嵌 LLM。」;
- `docs/adr/0004-calibration-via-claude-code-subagent.md` 已 accept「TeamBrain core 不调 LLM,所有 LLM 判断走 Claude Code Agent tool subagent」;
- 因此「blind verification」+「calibration」+「`/review` skill」其实都是同一类 primitive:Claude Code agent-tool 派出的临时 LLM。

**Recommendation**:
- 不引入新名字;policy §1.2 的角色更名为 **Verification subagent**(与 Calibration subagent 同源,只是职责不同;前者评 fix 正确性,后者评 rule maturity tier);
- 在 `docs/CONTEXT.md` 的 `### Calibration & tier` 节后追加新节 `### Verification subagent`,写明「Verification subagent ≠ /review skill ≠ Calibration subagent;三者均为 host-agent 进程内的 Claude Code Agent-tool 派生 subagent,但调用时机/输出/写入对象各异」(三联表见 §13);
- TeamBrain 进程仍 LLM-free;Verification subagent 的调度入口位于 `/fixed-flow-driver` skill 内部(step 4 `/review` 循环里 spawn),**不**进 `packages/core/`、**不**进 `packages/cli/`。

## 3. 「Haiku docs gate」⊥ MiniMax-M2.7-highspeed default + claudefast convention

**Q**: policy §11 写死命令 `claude -p --model haiku "what is the right api for xxx"`,要求公共 API 文档变更后必须由 haiku 答出 old API / new API / deprecation warning 三件套。

**Conflict**:
- 用户级 `~/.claude/CLAUDE.md` 默认模型是 `MiniMax-M2.7-highspeed`,非明确指定不切 sonnet/haiku/opus;
- `docs/CLAUDEFAST.md` + `docs/feature-verification.md` 的 canonical 验证命令是 `claudefast -p`,内部走 MiniMax-Anthropic-compatible profile,token 写在 wrapper 内,**永远不暴露**;直接写 `claude -p --model haiku` 会绕过这个约定,且默认环境下就拿不到 token;
- ADR-0007 把「PR-time 验证」的权威 probe 锁在 `claudefast -p "what should we do when we make a PR?"`,以 `/review`-anchored answer 作通过条件,**不**走 haiku 单独路径。

**Recommendation**:
将 §11 的命令统一改为:

```bash
claudefast -p "what is the right api for {feature_or_module}? answer in the form: old API / new API / deprecation warning"
```

通过判据三段(old / new / deprecation)保留;模型选择由 `claudefast` wrapper 内部决定,policy 不写死。如果未来因 cost 原因需要降到 haiku,通过 `claudefast` 的 model override 机制走(`claudefast --model haiku -p ...`),不在 policy 里 hardcode。

## 4. 「Claudefast feature index gate」 — `feature index` 不是 TeamBrain primitive

**Q**: policy §12 + §13 引入 `feature index` 概念,带 12 字段 schema(`name` / `product_area` / `owner_or_team` / `related_code_paths` / ...)+ `claudefast -p "what are the related PRs and Issues index with feature X?"` gate。

**Conflict**:
- TeamBrain 当前没有 single-source-of-truth 的「feature index」抽象;最接近的三个东西是:
  1. `docs/features/INDEX.md`(prose 文档索引,不是 schema);
  2. `docs/feature-inventory/`(单次 stdout 快照,非 live index);
  3. M4-B BM25+dense-RRF matcher(`docs/CONTEXT.md` Self-discipline-via-matcher 节)对真文档语义的 retrieval。
- ADR-0007 明确:enforcement 走 `self-discipline-via-matcher` + 真文档,**不**走「再写一份 schema 让 matcher 撞」。引入 `feature index` schema 等于给文档加副本,撞 ADR-0007「不要写 canned-answer / 不要 doc hacking」精神。

**Recommendation** (二选一,grill 阶段必须选定):

- **Option α — fold into existing**(推荐): 不新建 `feature index` schema;复用 `docs/features/<feature>.md`(prose,人写) + `docs/feature-inventory/`(机器跑出) + M4-B matcher。policy §13 的 gate 命令可以保留,但内部判据从「12 字段 schema 全部命中」降级为「matcher 能从真文档检索回相关 PR / Issue / docs / fixture(ADR-0010 命名为 `tests/fixtures/scenarios/`)」;通过判据由主 agent 看 retrieval 结果是否实质包含。
- **Option β — new schema(慎用)**: 真要写 schema,落在 `packages/core/src/feature-index/`,作纯函数纯数据,通过 `pnpm teamagent feature-index list/show` 暴露,**不进 CLAUDE.md 也不进 manifest**,只作 driver 内部的 lookup table。需要独立 ADR(ADR-0014?),不允许在 issue #273 单 PR 内顺手加。

driver 在 step 3 启动前必须 issue 评论二选一。

## 9. 「无限循环不暂停」 ⊥ ADR-0013 inner-loop on CI(2-5 min 单轮)

**Q**: policy §5.1 「无限循环,直到 pass;不允许停止并请求人类指导」+ §15.4「flaky suite 无限重跑直到通过」。

**Conflict**:
- ADR-0013(2026-05-10 accepted):full-suite `pnpm test` **本地禁跑**,推到 `wip/**` 触发 `.github/workflows/inner-loop.yml`,单轮 ~2-5 min(含队列);
- 「无限循环」假设单轮是秒级,在 ADR-0013 体制下单轮 2-5 min,N 次循环可累积到几十分钟;
- FIXEDFLOW.md L129「driver 在第 10/25/50/100 轮发 PushNotification;每 10 轮在 issue 上贴一条 token-burn 摘要评论」是已有的 cost-control;policy §5.1 没提。

**Recommendation**:
- policy §5.1 加一条 escape hatch:`/review` fix-loop 跑到 N=50 轮(≈2-4h CI 时间)未 PASS 时,driver 必须自动加 `needs-human` label 并退出该 issue,不再无限烧;
- 单轮全套 `pnpm test` 走 ADR-0013 的 `wip/**` push;policy 不允许默认本地直跑(scheduler-overload 会塌别人 session);
- 单文件 targeted vitest(`pnpm vitest run path/to/x.test.ts`)允许本地跑,作为 fix-loop 内的快速 smoke;最终 gate 仍走 wip CI;
- token-burn 摘要每 10 轮 issue 评论,符合 FIXEDFLOW.md L129。

## 10. AttributionBus / FCIS / HookShell 集成 — Verification subagent 的物理位置

**Q**: policy §1.2 没说 Verification subagent 怎么 plug 进现有 8 hook channel 与 AttributionBus。

**Conflict**:
- ADR-0008「HookShell as the deepening of 8 bin-*.ts imperative shells」:8 个 hook channel(PreToolUse / PostToolUse / UserPromptSubmit / Stop / PreCompact / SessionStart / SessionEnd / Updater)走共享 imperative shell;
- ADR-0009「Delivery mode as metadata」:user-visible 副作用全走 `bus.emit({...})`,**禁止** `process.stderr.write`;
- CLAUDE.md 元约束「Functional Core, Imperative Shell」:`packages/core/` 禁 import `fs` / `node:child_process`。

**Recommendation**:
- Verification subagent **不**进 `packages/core/`(它要 spawn child、读文件、跑命令,纯非纯函数);
- **不**进 `packages/cli/`(它由 `/fixed-flow-driver` skill 调,不通过 `pnpm teamagent` CLI 命令暴露);
- 落在 **`/fixed-flow-driver` skill 内部** 的子 agent,通过 Claude Code Agent tool spawn(per ADR-0004);

- 如果未来要把 Verification subagent 触发挂到 PostToolUse hook(每 fix commit 后自动跑),走 ADR-0008 的 HookShell `runHook` API;但 issue #273 落地版本**不**做这一步,留独立 ADR。

## 14. 落地位置 + driver 实施分阶段

**Q**: 这个 policy 是「写一份 docs」、还是「真要塞进 `/fixed-flow-driver` skill 让它运行时遵循」?driver 起 worktree 后第一步该干什么?

**Conflict**:无,但 grill 阶段必须冻结 scope,否则 driver 会跑偏(参考上一轮我作 `/claim-to-merge` routing 时给的 「风险 A / B」)。

**Recommendation**:
issue #273 的合理 scope = 三件事,不多不少:

1. **`docs/AGENTIC-CODING-POLICY.md` 新建**(取代 grill comment 的 standalone policy,作 in-repo SSOT;以本评论 §1-13 的 resolution 为准,**不**搬上一条 /grill-me 原文进 repo,不复制 §19 那一坨 yaml);
