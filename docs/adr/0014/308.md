# 1. 最大产品问题：我们到底在服务谁？

## Grill 问题

TeamBrain 是给 individual developer 自己用，还是给 team lead 管理团队进展用？

## 可选答案

A. 只做 developer-local memory / hook 工具
B. 只做 leader 监控平台
C. developer 工具为底，leader dashboard 为上层产品
D. 两条产品线完全分开
E. 暂不决定，先做底层 hook

## 裁决

选 **C**，但产品叙事上优先说：

> **TeamBrain 是给 team lead 用的 AI work observability platform。**

底层还是 developer agent / hook / audio / statusline，但第一商业价值要落在 leader：

```txt
leader 不用问人，也能知道：
  谁现在在推进？
  哪个项目有风险？
  哪个人 / 哪个 issue 卡住了？
  今天每个成员在每个项目上做了什么？
```

原因是 #309 明确不是在问“做一个漂亮 UI”这么简单，它说“等前端去做个花里胡哨的界面，然后我们再给界面补后端”，这其实是在逼问 app 怎么证明自己能给小 B leader 提效。citeturn138076view5

所以首页不能先放配置中心，也不能先放 statusline 美化。首页必须证明三件事：

```txt
1. 当前谁 / 哪个项目正在动？
   -> #308 green light

2. 哪里异常，需要 leader 介入？
   -> #372 live inspection / incident

3. 今天做了什么？
   -> #371 member × project daily summary
```

# 2. #308 的真实含义：不是日报，而是 green light + prompt evidence

## Grill 问题

`SessionStart` 和 `UserPromptSubmit` 发服务器之后，到底用来干什么？

## 可选答案

A. 作为日报正文主来源
B. 作为实时 active/idle green light
C. 作为异常检测辅助信号
D. 作为 prompt 原文证据回放
E. B + C + D，不做 A

## 裁决

选 **B + C + D**。

也就是：

```txt
#308 用途：
  1. leader 首页立即显示 green light
  2. 支持异常检测：高 AI activity + 低 GitHub progress
  3. 存完整 prompt，作为 evidence / replay

#308 不做：
  不作为 #371 日报的主数据源
```

#308 的 issue body 非常短，只说“暂定 session start 和 usersubmit prompt 事件发给服务器”；这意味着它是一个事件上报底座，不应该被误解成完整日报系统。citeturn138076view4

## 设计结果

```txt
收到 SessionStart:
  member × project green light 立即变绿

收到 UserPromptSubmit:
  green light 续绿
  raw prompt 完整写入 raw_events
  normalized_event 生成 summary/tags/session/work_item hints

收到 Stop:
  presence 变 offline，或 session closed
```

# 3. prompt 原文是否完整存储？

## Grill 问题

既然 leader 要看 prompt evidence，`UserPromptSubmit` 是否只存 metadata？

## 可选答案

A. 只存 metadata
B. 存 redacted prompt
C. 存 summary，不存原文
D. 完整存 raw prompt
E. 默认 metadata + summary，leader 可选 raw

## 裁决

根据你前面的回答，选 **D：完整存 raw prompt**。

但显示层要可配置：

```txt
存储：
  raw prompt full store

展示：
  leader 可配置展示哪些字段
  可配置首页是否展示 prompt
  可配置异常详情是否展开 prompt
  可配置日报是否附 prompt evidence link
```

关键是分清楚：

```txt
store full
≠ everywhere display full
```

完整存储解决 evidence / replay；展示策略由 leader / plugin 配置决定。

# 7. #372 异常状态：不是后台永远重度采集，而是 leader 点击后 live inspection

## Grill 问题

#372 要不要一直后台计算所有成员所有项目的异常？

## 可选答案

A. 是，所有项目持续重算
B. 否，只点开时查
C. #308 green light 常驻，#372 点击后深入收集
D. 只做日报，不做实时
E. 只做 GitHub，不看 AI events

## 裁决

选 **C**。

#372 的需求是 leader 需要知道项目成员的异常状态，并对项目整体作用有完整认知；这不等于每秒后台重算所有成员的所有 GitHub 和 prompt。citeturn138076view10

正确模型：

```txt
首页常驻：
  #308 green light
  low-cost presence

leader 点击成员 / 项目 / green light：
  启动 live inspection session
  拉最近 GitHub activity
  拉相关 #308 AI events
  关联 work item
  生成 progress / abnormal summary

发现异常：
  冻结成 incident record

未发现异常：
  session 结束后只保留必要 telemetry
```

默认窗口：

```txt
点击成员：
  最近 24 小时

点击项目：
  最近 7 天

点击 issue / PR：
  从 issue / PR 创建时间开始

点击 green light：
  当前 session + 最近 24 小时
```

# 8. 异常检测的第一条规则：高 AI activity + 低 GitHub progress

## Grill 问题

什么叫“卡住”？

## 可选答案

A. prompt 次数多
B. GitHub 长时间无更新
C. AI 活跃很高，但 GitHub 没有进展
D. leader 手动标记
E. C 为默认，leader 可配置阈值

## 裁决

选 **E**。

默认 stuck detector：

```txt
if ai_prompt_count >= 5
and github_progress_events == 0
within 60 minutes
then severity = warning

if ai_prompt_count >= 10
and github_progress_events == 0
within 120 minutes
then severity = critical
```

GitHub progress events：

```txt
commit
pr_opened
pr_updated
issue_comment
review_submitted
branch_pushed
status_changed
```

这符合 #372 的“异常状态”，也符合 #308 只是 AI event source 的边界。citeturn138076view10turn138076view4

# 11. green light：presence state，不是完整进展判断

## Grill 问题

#308 green light 什么时候亮？

## 可选答案

A. SessionStart 后一直绿
B. UserPromptSubmit 后续绿
C. Stop 立即灰
D. active / idle / offline / error 四态
E. D + TTL 可配置

## 裁决

选 **E**。

```txt
green active:
  最近有 SessionStart / UserPromptSubmit

yellow idle:
  session 开着，但 N 分钟没有 UserPromptSubmit

gray offline:
  收到 Stop，或 TTL 过期

red error:
  hook 上报失败
  agent 掉线
  GitHub 绑定缺失
  事件解析失败
```

默认：

```txt
active_ttl = 10 分钟
idle_after = 10 分钟无 UserPromptSubmit
offline_after = 60 分钟无任何事件
Stop = 立即 offline
```

这把 #308 做成 leader 首页的即时信号，而不是误做成完整进度分析。#308 的原始需求只说发 `session start` 和 `usersubmit prompt`，所以它最适合做 presence。citeturn138076view4

# 22. #320：它不是产品设计主线，是 evidence / coding discipline

## Grill 问题

#320 要不要决定 #308/#371/#372 的产品设计？

## 可选答案

A. 要，所有功能必须围绕 #320 设计
B. 不要，#320 只是文档
C. #320 是 business feature 证明体系，不反向决定产品主线
D. #320 应该延期
E. #320 应该删除

## 裁决

选 **C**。

你前面纠正得对：#320 是 coding/detail/evidence 线，不是 leader 产品设计主线。

#320 要求一个 probe 返回三大 business feature 和四层证据 verdict：CEO / Coder / Machine-readable / LLM-readable raw；它还提到 `docs/BUSINESS-FEATURES.md`、README 三大业务特性、`CLAUDE.md`/`AGENTS.md` canned-answer rule、grep anchors、CHANGELOG 等。citeturn148789view4

它应该给每个业务功能提供证明：

```txt
CEO:
  这个功能解决什么业务问题

Coder:
  哪些文件 / hooks / commands / routes 实现它

Machine-readable:
  JSON / SQL / CLI --json / DB schema 能证明它

LLM-readable raw:
  docs / logs / raw artifacts / canned answer anchors
```

但它不能反过来规定：

```txt
#308 必须怎么设计
#371 必须从 prompt 生成
#372 必须实时后台采集
```

#320 的位置是：

```txt
after design:
  add evidence anchors
  add canned answer
  add docs
  add --json / grep anchors
```

不是：

```txt
before design:
  force product shape
```
