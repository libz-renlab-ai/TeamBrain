## ① Task description

Land a coordinated three-part change so `curl -fsSL .../release/install.sh | bash`
on `origin/release` becomes the **P4-hardened** installer (URL-pinned, SHA-256
verified, two-step, redirect-guarded, fallback-aware, dry-run capable) while
keeping the existing POSIX-sh `curl | sh` flow alive for backward compatibility.

Three changes, all on this branch (`worktree-issue121`):

1. **Rename + add side-by-side** in repo:
   - `release/install.sh` (current POSIX sh, 3804B) → renamed to
     `release/install-legacy.sh` on `main` (still bot-published to
     `origin/release` for BC).
   - `release-prep/install.sh.draft` (current 8256B P4 bash) → copied into
     `release/install.sh` (becomes the new published entry point).
   - New `release/install.sh.sha256` generated by `release-prep/gen-sha256.sh`
     and committed; the bot regenerates on every push for freshness.

2. **`.github/workflows/release-branch.yml` upgrade** (single workflow file, **3a chosen**):
   - Stage `release/install.sh` (the P4 one) at staging root.
   - Stage `release/install-legacy.sh` at staging root for BC.
   - Run `release-prep/gen-sha256.sh release/install.sh /dev/null` in the job
     to produce `install.sh.sha256` and stage it at staging root.
   - `chmod 0755` both `install.sh` and `install-legacy.sh`.
   - **(REQUIRED — 3a)** Detect version from `packages/teamagent/package.json`,
     check if GitHub Release tag already exists (idempotency guard), and on
     first push for a new version: build tarball via `pnpm pack`, generate
     tarball SHA256, then `gh release create v${VERSION}` uploading
     `teamagent-v${VERSION}.tgz` + `teamagent-v${VERSION}.tgz.sha256` +
     `install.sh.sha256` as Release assets.
   - Existing force-push to `release` branch step is preserved unchanged.

3. **`release-prep/install.sh.draft` tarball fallback chain** (kept as
   belt-and-suspenders even with 3a) — extend `_download_with_fallback` so
   when the GitHub Release asset URL
   (`releases/download/${TAG}/teamagent-${TAG}.tgz`) returns 404 (e.g. user
   pinned a `TEAMAGENT_VERSION` that pre-dates this PR), the script degrades
   to `archive/refs/heads/release.tar.gz` (the path the legacy POSIX
   installer uses today). The same change is applied to `release/install.sh`
   on `main` (since `release-prep/install.sh.draft` is the source-of-truth
   that gets copied during the rename). Even with 3a's real Release pipeline,
   keeping this fallback costs ~10 lines and protects against missing assets.

### What we're explicitly NOT doing

- **No self-update** (issue #84 §H6 punt). `TEAMAGENT_VERSION` env var still
  pins a tag, but no auto-upgrade logic.
- **No external CDN mirror** (issue #84 §H5 resolution stands — GitHub
  Release asset is the only fallback).
- **No deletion** of the legacy POSIX installer. It moves to
  `install-legacy.sh` so existing `curl | sh` users who somehow hit the
  legacy URL still get a working install.
- **No force-push** to `origin/release` from this PR. The release-branch
  workflow keeps that authority; this PR only edits the workflow file
  + repo files.
- **No changes** to `packages/teamagent/postinstall.mjs` or the build
  pipeline. install.sh is the only delivery path under audit.
- **No changes** to `.github/workflows/ci.yml` or other workflows.

## ④ TEAMWORK slicing — N+1+(2N) execution plan

## Risks

- **Bot push race**: if the workflow runs concurrently with a manual push to
  `origin/release`, force-push wins. Mitigated by AGENTS.md rule "no manual
  pushes to `origin/release`" (already in issue body). Still, document in
  report if the PR's first deploy hits a race.
- **`bash -s -- --dry-run` shell quoting**: piped to `bash` from `curl`, the
  `-s --` separator can be eaten by some shells. Worker B probe P2 must
  verify by actually piping (in a sandboxed test harness, not against
  origin/release directly).
- **sha256 freshness drift**: if the bot regenerates `.sha256` on every
  release-branch publish, but a user pinned `TEAMAGENT_VERSION=v0.9.3`, the
  fetched `install.sh.sha256` is for v0.9.4's install.sh content. Mitigated
  because install.sh content is version-agnostic; sha256 covers the script
  bytes, not the tarball it fetches.
- **Worker C self-grading**: judge.md is written by Worker C. Worker C must
  not also be the §V3 judge LLM. Lead enforces this by spawning the §V3
  probe as a fresh `claudefast -p` invocation, not via SendMessage to
  Worker C.

## After approval — execution sequence

1. Lead resolves Open questions 1–5 with user (or accepts defaults).
2. Lead spawns Workers A/B/C in **a single Agent tool call** (parallel).
3. Each worker runs its 2 probes; reports back to lead.
4. Lead spawns Reporter (opus 1M); awaits PASS/FAIL.
5. On PASS: `/commit-commands:commit-push-pr` → opens normal PR → POSTPR
   loop runs `/review` until PASS.
6. On `/review` FAIL: write `docs/plans/2026-05-08-issue-121/pr-<n>-fix-plan.md`
   per `docs/PR-PLAN.md` strict shape, run TEAMWORK again on that slice,
   push to same PR branch, loop.
7. Stop only when CI green + no conflicts + `/review` PASS + Codex silent/👍.
