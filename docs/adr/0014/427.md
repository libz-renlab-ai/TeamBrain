## Background: what is the problem

`CLAUDE.md` at HEAD is 321 lines / 88 KB / ~39 K tokens, of which ~78% (lines 1-160) is a single "参考文档" mega-bullet list of ~36 anchor-sentence canned-answer rules. Each rule contains: trigger keyword set, verbatim anchor sentence, judge-harness `grep -F` substring anchors, paraphrase counter-examples, and a link to `docs/<RULE>.md` for the full playbook.

This list grows every PR (recent additions: #413 visual-proof-pr, #409 VISUAL-PROOF-FORMAT, #412 3-methods-workflow), is loaded as system context on every session start, and contains visible redundancy across 4 thematic clusters.

## Decisions (7 questions × 7 answers)

### Q1 — How does the baseline probe define "PASS"?

**Decision: option C — floor method.** Run the probe across all 36 anchor rules and classify each into:

- `WORKING_BEFORE` (current CLAUDE.md emits all required anchor substrings when probed with the trigger) — must NOT regress after any cluster merge
- `BROKEN_BEFORE` (current CLAUDE.md fails to emit required anchors) — recorded as exemption, not blocking, NOT fixed in this PR

`PASS` for a single rule = `grep -F` over the merged CLAUDE.md (and/or the model's response when the trigger is asked) hits every required substring anchor declared by the rule. No LLM-as-judge in the loop, per the E2E-LEARNING rule ("deterministic numbers or bytes — no LLM-as-judge in the loop, so the model cannot fabricate a pass").

### Q1b — Are BROKEN_BEFORE rules fixed in this PR?

**Decision: option A — strict no.** This PR's task is the merge refactor. Mixing in "fix broken anchors" expands scope, violates the FIXEDFLOW "1 PR = 1 task" principle, and makes `/review` push back. BROKEN_BEFORE rules get follow-up issues; each goes through its own grill cycle because the root cause is rule-specific (anchor text outdated vs rule itself stale vs model drift).

**Edge case carve-out**: if a cluster merge cannot be performed without modifying a BROKEN_BEFORE anchor (e.g., the rule references a deleted concept), pause that cluster, file a priority follow-up issue, and proceed with the next cluster.

### Q2 — What is the cluster merge order, and can any of it run in parallel?

**Decision: canary-first order C4 → C2 → C1 → C3.** Justification:

- **C4 first (2 cards, lowest risk)**: validates the merge mechanism with the smallest blast radius. Anchor strings disjoint, merge = a 2-row table.
- **C2 second (4 cards, low risk)**: the "I am not the other 3" boilerplate is obvious dead weight; removing it is mechanical.
- **C1 third (8 cards, highest risk)**: requires constructing a unified timeline diagram and embedding 8 sets of verbatim anchors. Worth doing only after the mechanism is proven on C4 + C2.
- **C3 last (6 cards, medium risk)**: overlaps with C1 (FIXEDFLOW) and C2 (VISUAL-PROOF-FORMAT, VISUAL-PROOF-PR). Doing it before C1/C2 would require editing the overlapping rules twice. Strict ordering avoids rework.

**Parallelism**:

- ❌ Cluster merges run **serially** (single file, single PR, FIXEDFLOW "1 PR = 1 task").
- ✅ Baseline + regression probes run **in parallel** (`grep -F` over the same file in process is independent per rule; trivially batchable).
- ✅ Optional Agent-tool subagent prep (read source cards, draft merged-card structure) can run in parallel per cluster.

### Q3 — How is "verbatim anchor preservation" reconciled with "merged card not bloated"?

**Decision**: verbatim anchor sentences are embedded as table cells / numbered list items inside the merged card body. Required `grep -F` substrings remain **bit-identical**. Each merged card body MUST be ≤ 2× the size of the single largest source card (a hard budget that forces real compression, not just stapling cards together).

Specific structural patterns:

- **C1 (lifecycle)**: ASCII timeline diagram (phases P0 → P6) with anchor strings embedded at each phase row.
- **C2 (HTML)**: 3-column table (local pop-open / PR-shipped / ask-user) with anchor strings as cell contents.
- **C3 (workflow)**: 2-row method-comparison table (Symphony / fixed-flow) + a single visual-proof overlay paragraph, with anchor strings inline.
- **C4 (permission)**: 2-row table (review subagent / claimed worktree) with anchor strings as cell contents.

### Q4 — Is cluster C4 really the lowest-risk canary?

**Decision: yes.** Verification: the two cards' substring-anchor sets are fully disjoint:

- REVIEW-SUBAGENT-PERMISSION anchors: `no need`, `/review`, `subagent`, `ADR-0007`
- CLAIMED-WORKTREE-NO-PERMISSION anchors: `NO` (case-sensitive uppercase), `claimed`, `worktree`, `FIXEDFLOW`, `standing approval`

There is zero collision and the rules target different trigger keyword sets (`/review` + `subagent` vs `worktree` + `claimed` + `FIXEDFLOW + start`). Merging the two into one card with a 2-row table cannot create cross-talk: a `/review`-shaped trigger still hits only the row whose anchors contain `/review`.

### Q5 — Regression threshold?

**Decision: zero tolerance on the `WORKING_BEFORE` set.** Concretely: if pre-merge baseline shows N rules in `WORKING_BEFORE`, then post-merge probe MUST show all N still passing. Any single regression triggers a rollback of that cluster's merge commit (`git revert <sha>` or `git reset --hard HEAD~1` before push), the cluster is re-attempted with a different structural approach, and the verification HTML records both attempts.

Counter-example tolerated: a `BROKEN_BEFORE` rule remains broken after merge → not a regression, not a failure.

### Q6 — 1 PR or 4 PRs?

**Decision: 1 PR.** Justification per `docs/TRIAGE-AND-SPLIT.md` Single-PR Shippable Test:

- (1) ≥2 independent expected outputs? **Borderline yes**, but all outputs touch one file with a unified theme.
- (2) Cross-package dependencies? **No** — single file.
- (3) Cross-team boundaries? **No**.
- (4) Grill says "split"? **No**.
- (5) Estimated diff > 1500 LOC or > 30 files? **No** — projected ~500 LOC in 1 file.
- (6) Draft `/review` flags cross-area P1/P2? **Unlikely** — entire diff is in one document section.

Operational shape: 4 commits (one per cluster, each titled `refactor(claude-md): merge cluster-C{N} ...`), then squash-merged. Per-cluster regression probes attached to each commit's body.

### Q7 — Why are the remaining ~19 cards left untouched?

**Decision**: a re-audit found 2 additional weaker clusters NOT in scope:

- **Cluster X — commit/merge sequence (3 cards)**: COMMIT-FLOW + POSTPR + BEFORE-MERGE. All describe sequential steps from "edit complete" to "branch deleted". Sequential, not redundant — each card describes a distinct phase. Marginal merge gain, defer.
- **Cluster Y — plan docs (3 cards)**: PLAN-RESEARCH-REPORT + HOWTO-PLAN-PR + PR-PLAN. Describe pre-PR (HOWTO), pre-PR planning structure (PLAN-RESEARCH-REPORT), and post-PR fix planning (PR-PLAN). Some overlap on "three-section structure" but each addresses a different lifecycle phase. Marginal merge gain, defer.

Both deferred to follow-up issues post-#427 merge.

Remaining ~13 cards are genuine singletons covering orthogonal topics (BUSINESS-FEATURES, E2E-LEARNING, PR-ISSUE-COMMENT-LANGUAGES, ISOLATED-WORKTREE, ISSUE-TRACKING, INIT-PROPAGATION, PUBLISHING, etc.). No redundancy with other cards.

## Verification scope adjustments (post-grill discoveries)

Two hard blockers were discovered during grill close-out and resolved without re-grill:

### Blocker 1 — `claudefast` not installed on Windows host

The original plan invoked `claudefast` to run trigger prompts against a fresh session, then `grep -F` the response. On this Windows machine `claudefast` is absent (`which claudefast` → `command not found`).

**Resolution**: switch to **mechanical `grep -F` directly over the merged `CLAUDE.md` file content**. This is precisely the judge harness all CLAUDE.md rules self-declare ("Judge harness must case-insensitive substring grep all N anchors"). Mechanical probe is deterministic, free, instant, and is the canonical evaluator per CLAUDE.md's own rules. It is also more faithful than runtime probing because runtime probes have model nondeterminism.

### Blocker 2 — No `<username>.github.io` for either proposer account

Strict VISUAL-PROOF-PR requires hosting on `https://<username>.github.io/<artifact-repo>/...`. Neither `libz-renlab-ai.github.io` nor `liboze2026.github.io` exists.

**Resolution**: VISUAL-PROOF-PR rule is **gracefully waived** for this PR. Per `docs/3-METHODS-WORKFLOW.md`, method 3 (visual-proof overlay) is "applied whenever the change has visual side effects (UI / dashboard / screenshot / demo / chart / video)". This PR is docs-only with zero UI side effects; the verification HTML is internal QA, not user-facing visual proof.

Artifacts go to: `docs/plans/2026-05-13-issue-427-claude-md-slim/verification.html`, `screenshots/*.png`, `report.gif`. Reviewer opens via `raw.githack.com` link in PR body, or by cloning the branch locally. POP-OPEN-HTML rule still applies for the local-pop-open copy in `/tmp/teamagent/issue-427/`.

## How to evaluate (judge harness, written before implementation)

This PR is evaluated by the following bytes-or-numbers tests; an LLM-judge is not in the loop.

1. **Anchor preservation** — `bash scripts/probe-claude-md-anchors.sh` (created by this PR) outputs JSON of shape `{rules: [{rule_id, anchors: [{substring, present}], status: WORKING|BROKEN, baseline_status: WORKING|BROKEN}]}`. The harness asserts: for every rule with `baseline_status == "WORKING"`, post-merge `status` is also `WORKING` (zero regression on WORKING_BEFORE set).
2. **Token-budget delta** — `wc -c CLAUDE.md` before and after must decrease by ≥ 15%. Lower bound: 33 K bytes post-merge.
3. **Cluster cardinality** — `grep -c "^- \*\*" CLAUDE.md` (counting bold-prefixed bullet entries in the reference-docs section) drops by ≥ 12 entries.
4. **Anchor substring preservation** — for each anchor declared by any rule, `grep -F "<anchor>" CLAUDE.md` returns ≥ 1 hit. Aggregate substring-coverage: ≥ 100% of WORKING_BEFORE substrings present.
5. **Verification artifacts present** — `test -f docs/plans/2026-05-13-issue-427-claude-md-slim/verification.html` AND `test -d docs/plans/2026-05-13-issue-427-claude-md-slim/screenshots` AND `test -f docs/plans/2026-05-13-issue-427-claude-md-slim/report.gif`.
6. **POP-OPEN-HTML compliance for /tmp copy** — verification HTML pop-opened from `/tmp/teamagent/issue-427/` (not from project tree).

Pass = all 6 tests pass. Failure of any one rolls back the affected cluster.
