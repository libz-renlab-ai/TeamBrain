## Problem Statement

TeamAgent 当前依赖两条用户主动渠道获取系统反馈：

1. `bash scripts/bugreport-collect.sh` + 用户主动贴 GitHub issue
2. `/pitfall` 主动录入

**沉默错误**（用户遇到问题但**不主动报**）落不进任何渠道。在 intrapreneurship 语境下，领导对此有具体担忧：「用户报 bug 能定位 / 不能让用户踩坑了我们不知道」。需要建立中央化日志收集机制，让团队（含领导）可以基于客观运行数据做修复、优先级、风险响应决策。

## Demand Evidence

> 强度评估：**弱-中**。基于 D1-D8 office-hours 探询。

- ✅ **真实驱动存在**：领导命令（intrapreneurship 合法 customer），具体担忧偏 bug/质量类（D6 答 C）
- ⚠️ **未验证**：领导**原话**与"偏 bug/质量"理解的一致性。建议先做 30 分钟对齐（见 Assignment）
- ❌ **缺失**：第一批外部团队的具体姓名（D5 第一轮答 A "≥3 个"，第二轮 push 后承认给不出）。意味着 MVP 上线时**数据集为空**，至少 N 周后才会有真实输入
- ⚠️ **隐私态度修正**：原始表态「不在乎隐私」（D8）→ 经 push 修正为"封闭部署 + 用户书面同意 + 数据不出墙"路径（D8 答 A）。此假设为 design 关键 premise，需要在执行前验证 4 个具体边界条件（见 Premises 4-7）

## Target User & Narrowest Wedge

**真实"customer"**（按优先级）：

1. **领导**（一级 customer）：要 bug/质量信号做产品决策、向上汇报
2. **TeamAgent 开发团队**（二级 customer）：要 bug 复现上下文做修复

**第一批外部团队（数据源）**：D5 push 第二轮承认给不出具体姓名。design doc **假设 0 个外部团队**——MVP 上线时数据集为空。

**Narrowest wedge**：在用户已签书面同意 + 部署在封闭环境的前提下，**只上报错误信号 + 用户主动一键反馈**两个最小通道。先不做"全行为采集"。先用真实运行 6-8 周看：(a) 领导是否还在意；(b) 数据是否真的驱动决策（D3 答 1+2 的兑现率）。

## Constraints

- **平台**：TeamAgent 是 CLI / Node.js 工具，分发 = HTTPS tarball。客户端上报必须不破坏离线运行（断网不应阻塞 CLI）
- **隐私**：见 Premises 4-7
- **服务器**：尚不存在。新建需要域名 / SSL / 部署平台 / 监控 / 备份策略
- **预算**：未明示，按 ≤1 个月工程量估
- **法律**：中国 PIPL 适用；如果用户在跨境环境，可能触发跨境数据传输评估

## Premises（2026-05-06 状态：口头已确认，待书面留底）

> ✅ = 用户口头确认成立 ❌ = 不成立 ⚠️ = 待补书面证据

| # | Premise | 状态 | 待补证据 |
|---|---|---|---|
| 1 | 领导是真实 customer，明确让你做 | ✅ + ⚠️ | 钉钉文字 / 邮件 / 会议纪要 |
| 2 | 领导关心 bug/质量类信号（D6 答 C） | ✅ | （注：实际确认范围扩大到"所有信息"，see #7） |
| 3 | 沉默错误是真实问题 | ✅ | 此前 D3 答 1+2 中已隐含 |
| 4 | 部署边界封闭（团队内 / 内网） | ✅ + ⚠️ | 部署边界文档（哪些 IP 段是"墙内"，跨墙路径阻断） |
| 5 | 用户书面同意已存在或可获得 | ✅ + ⚠️ | "团队成员全部统一了" → 需要落到**同意书签字**或群消息+邮件留底 |
| 6 | 数据不出墙 | ✅ + ⚠️ | 数据流向图 + 第三方服务合规审计结论 |
| 7 | 领导对"完整日志"有书面授权（含 prompt 内容、git diff） | ✅ + ⚠️ | "可以收集所有的信息到服务器" → 需要领导**书面确认**这一句的范围 |

**⚠️ 警告**：所有 ⚠️ 项现在都是**口头**。在合规审计 / 项目交接 / 出现纠纷时，**口头不算**。在开工前的 1-2 天内，**必须**把这些 ⚠️ 转成 ✅（链接 / 截图 / 文件）。这不是 paranoid，是 intrapreneurship 项目最常见的死法：

- 口头确认 → 6 个月后领导换岗 → 新领导问"谁批的？" → 你拿不出 → 项目暂停 / 担责
- 口头团队统一 → 1 年后某成员离职 → 新成员发现"我没同意上传我的代码" → 投诉 → 法务介入

**风险等级**：从"项目级雷"降到"程序级风险"，但**没消失**。Assignment 第 1 条专门处理这件事。

## Approaches Considered

### Approach A: 异常 / 错误信号最小上报

**上报范围**：未捕获异常 + stack trace + 错误码 + 命令名 + OS / TeamAgent 版本号 + 退出码

**不上报**：prompt 内容、git diff、文件路径、知识库内容

**opt-in**：首次运行 prompt 同意 + `pnpm teamagent telemetry off` 关闭

**工程量**：3-5 天

- 优点：直接命中 D6 答案 C（沉默错误兜底），隐私风险最低，依赖 Premises 1-3 即可
- 缺点：拿不到 prompt 上下文，对 D6 之外的需求（如"多团队使用模式"）无信号

### Approach B: 一键反馈打包升级

`pnpm teamagent report-issue` 直接 HTTPS POST 到我们服务器（保留 GitHub issue 备份）。不主动收集，但出问题时极其顺手。

**工程量**：2-3 天

- 优点：隐私最低（用户主动选），复用现有 collector 80% 代码
- 缺点：对沉默错误**完全无效**（用户没意识到 bug 不会主动报）

### Approach C: 双通道（A + B）+ 完整日志可选上报

A 默认 ON，B 默认 ON，**新增**第三通道："完整日志"上报（含 prompt 内容、git diff、文件路径）——前提是 Premises 4-7 全部书面成立。

**工程量**：8-12 天

- 优点：完整覆盖领导担忧 + 多团队使用模式可见性
- 缺点：**强依赖 Premises 4-7 全部成立**。任何一条不成立 = 项目级合规雷

### Approach D（lateral）: 先 30 分钟对齐领导，再决定 MVP

半天准备 + 半天会议（4 个具体问题，见 Assignment）。**用 1 天换后面 5-12 天会不会白做**。

## Recommended Approach

> **2026-05-06 update**：领导口头确认 + 团队口头统一后，推荐路径从 ~~D→A~~ 升级到 **C（双通道+完整日志）**。

**主推：C（双通道+完整日志）**

理由：

- D 步骤已完成（用户反馈：领导口头确认 + 团队口头统一）
- Premises 4-7 由"待验证"改为"口头确认+待留底"
- 既然领导口头授权"所有信息"+ 团队"全部统一"，那 A 通道（异常上报）和 B 通道（一键反馈）都不再是"最小可行"，应该一步到位 C
- **但**前提是 Premises 表里的 ⚠️ 在开工前 1-2 天**全部转 ✅**。Assignment 第 1 条专门做这事

**实施顺序**（C 内部分阶段）：

1. **第 1 周**：完成 ⚠️ → ✅ 留底 + 服务器搭建（域名 / SSL / 部署 / 监控）
2. **第 2 周**：客户端 Approach A（异常上报，最小风险，先跑通端到端）
3. **第 3 周**：客户端 Approach B（一键反馈通道）
4. **第 4 周**：客户端"完整日志"通道（含 prompt 内容、git diff、文件路径）+ 客户端首次运行 opt-in prompt
5. **第 5-6 周**：内部团队 6 人全量上线 + 修第一波 bug
6. **第 7-8 周**：Success Criteria 复盘

**坚决不要省**：第 1 周的留底 + 服务器准备。直接从第 2 周开工 = 仍然在裸奔，只是省了 1 周后面被合规找上门多花 5 周。

## Success Criteria

**6-8 周后判断 MVP 是否成功**：

| 指标 | 阈值 |
|---|---|
| 沉默错误捕获率 | ≥1 次"用户没报但我们看到了"事件 |
| 修 bug 决策驱动次数 | ≥3 次"看了上报数据 → 改了某个具体 bug" |
| 上报通道稳定性 | 上报失败率 < 5% |
| 隐私零事故 | 无任何用户 / 法务 / 合规反馈"我看见我的内容被上传了，我没同意" |
| 领导满意度 | 领导能用上报数据**回答至少 1 次**他向上汇报的问题 |

任一指标不达标 → 触发 6-8 周复盘，决定是否撤销 / 升级 / 调整。

## What I noticed about how you think

> 4 个具体观察，反映不评判：

1. **「我们需要日志来修系统」和「领导让我做」是同一句话被你说了两遍**。第一次（D3）你把它包装成"修系统驱动"，第二次（D5/D6）push 出来才说"领导让做"。这个**重新包装的本能**值得注意——把上面的命令翻译成"我们的需求"是常见的，但有时候会让你**忘记自己在执行别人的指令**，开始**为这个指令辩护**而不是**澄清这个指令**。

2. **D5 你选了"3 个以上有具体姓名"，push 出来变成"给不出来"**。这一刻诚实交代是好信号——但提示你：**第一答案是给问问题的人听的，不是给你自己的**。下次自己脑子里跑 office hours 时，从"老实答"开始，别先 polish。

3. **D8 的"我不在乎隐私"是项目级红灯**。这句话没说出口的语义是「我现在只想完成"领导让我做"，不想节外生枝」。但 over-deliver 给领导制造合规风险，反过来会让你的项目被打回。**push 一次后你切到 A**——意识到风险存在、定义了一个 valid 的 A 子集来约束。这是好的修正反应。

4. **回答越来越短**。这是疲态信号。office-hours 一次走 8 题已经是上限。如果再次走，建议分两次：第一次定 problem + premises（D1-D6），第二次再做 alternatives + design（D7-D8）。带着已经写好的 design doc 去找领导，比再被我 push 8 题有用得多。
