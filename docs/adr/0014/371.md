# 1. 最大产品问题：我们到底在服务谁？

## Grill 问题

TeamBrain 是给 individual developer 自己用，还是给 team lead 管理团队进展用？

## 可选答案

A. 只做 developer-local memory / hook 工具
B. 只做 leader 监控平台
C. developer 工具为底，leader dashboard 为上层产品
D. 两条产品线完全分开
E. 暂不决定，先做底层 hook

## 裁决

选 **C**，但产品叙事上优先说：

> **TeamBrain 是给 team lead 用的 AI work observability platform。**

底层还是 developer agent / hook / audio / statusline，但第一商业价值要落在 leader：

```txt
leader 不用问人，也能知道：
  谁现在在推进？
  哪个项目有风险？
  哪个人 / 哪个 issue 卡住了？
  今天每个成员在每个项目上做了什么？
```

原因是 #309 明确不是在问“做一个漂亮 UI”这么简单，它说“等前端去做个花里胡哨的界面，然后我们再给界面补后端”，这其实是在逼问 app 怎么证明自己能给小 B leader 提效。citeturn138076view5

所以首页不能先放配置中心，也不能先放 statusline 美化。首页必须证明三件事：

```txt
1. 当前谁 / 哪个项目正在动？
   -> #308 green light

2. 哪里异常，需要 leader 介入？
   -> #372 live inspection / incident

3. 今天做了什么？
   -> #371 member × project daily summary
```

# 2. #308 的真实含义：不是日报，而是 green light + prompt evidence

## Grill 问题

`SessionStart` 和 `UserPromptSubmit` 发服务器之后，到底用来干什么？

## 可选答案

A. 作为日报正文主来源
B. 作为实时 active/idle green light
C. 作为异常检测辅助信号
D. 作为 prompt 原文证据回放
E. B + C + D，不做 A

## 裁决

选 **B + C + D**。

也就是：

```txt
#308 用途：
  1. leader 首页立即显示 green light
  2. 支持异常检测：高 AI activity + 低 GitHub progress
  3. 存完整 prompt，作为 evidence / replay

#308 不做：
  不作为 #371 日报的主数据源
```

#308 的 issue body 非常短，只说“暂定 session start 和 usersubmit prompt 事件发给服务器”；这意味着它是一个事件上报底座，不应该被误解成完整日报系统。citeturn138076view4

## 设计结果

```txt
收到 SessionStart:
  member × project green light 立即变绿

收到 UserPromptSubmit:
  green light 续绿
  raw prompt 完整写入 raw_events
  normalized_event 生成 summary/tags/session/work_item hints

收到 Stop:
  presence 变 offline，或 session closed
```

# 6. #371 日报：GitHub-first，不是 prompt-first

## Grill 问题

日报的主数据源是什么？

## 可选答案

A. prompt 原文
B. Claude/Codex session summary
C. GitHub activity
D. audio transcript
E. GitHub-first，AI/audio 作为辅助 evidence

## 裁决

选 **E，但主源是 GitHub**。

#371 的需求是“员工每天使用完 Claude 后，统一汇总他们在多个并行项目中的操作，通过一句话总结当天工作内容，形成每日工作汇报”。它说的是“多个并行项目中的操作”和“一句话总结当天工作内容”，不是“把 prompt 摘要发给老板”。citeturn138076view9

所以日报结构应该是：

```txt
主记录：
  member × project daily summary

项目首页：
  project daily summary

成员视角：
  member daily summary，可选

明细锚点：
  Issue > PR > Branch > Commit > AI Session
```

示例：

```txt
Alice / TeamBrain:
  今天推进 Codex hook 初始化幂等与 adapter 分离，已完成配置 merge 策略讨论，尚未合并 PR。

Bob / TeamBrain:
  今天排查 Windows audio 默认设备问题，确认应默认麦克风并提供 --device 逃生口。
```

日报不是：

```txt
Alice 今天问了 Claude 38 次。
```

日报应该是：

```txt
Alice 今天在 TeamBrain 的 #291 上推进 init --target=both 的幂等 hook 安装方案。
```

# 10. identity / project binding：不能靠猜

## Grill 问题

怎么把 GitHub activity 和 AI session 对到同一个人 / 项目？

## 可选答案

A. GitHub username
B. email
C. member_id ↔ github_login ↔ agent_install_id 显式绑定
D. commit author 自动猜
E. 不绑定，日报和异常各算各的

## 裁决

选 **C**。

```txt
member binding:
  member_id
  github_login
  agent_install_id
  team_id
  display_name

project binding:
  project_id
  github_org
  github_repo
  issue_scope
  branch_scope
  leader_ids
```

否则会出现：

```txt
GitHub 上 Alice 提了 PR
AI event 里是本机 user emily
日报不知道是不是同一个人

Claude session 在 repo A
GitHub commit 在 repo B
异常分析不知道属于哪个项目
```

#371 的“多个并行项目”天然要求跨 repo / project 绑定，#372 的异常分析也要求能从 AI event 追到项目上下文。citeturn138076view9turn138076view10

# 21. #310：手机 Web/PWA 一键录音，而不是只修 CLI

## Grill 问题

“不需要开电脑，随时开录”怎么实现？

## 可选答案

A. 只做 CLI
B. 只做移动 app
C. CLI + 手机 Web/PWA 共用 Audio Event API
D. 做 Slack/飞书 bot 上传
E. 先只改文档

## 裁决

选 **C**。

#310 的需求只有一句：“不需要开电脑，随时开录”。这意味着 CLI-only 不够。citeturn138076view6

架构：

```txt
Desktop:
  teamagent audio start/stop/import

Mobile:
  PWA 一键录音
  background chunk upload
  offline local cache
  retry/resume

Backend:
  Audio Event API
  transcription job
  summary job
  plugin dispatch
```

手机录音归属：

```txt
从项目页录音：
  直接挂 project

从全局快捷入口录音：
  先进 personal audio inbox

AI 自动归类：
  只建议 project/issue/PR
  不自动强绑定
```

避免 AI 错归类污染 #371 日报和 #372 异常。

# 22. #320：它不是产品设计主线，是 evidence / coding discipline

## Grill 问题

#320 要不要决定 #308/#371/#372 的产品设计？

## 可选答案

A. 要，所有功能必须围绕 #320 设计
B. 不要，#320 只是文档
C. #320 是 business feature 证明体系，不反向决定产品主线
D. #320 应该延期
E. #320 应该删除

## 裁决

选 **C**。

你前面纠正得对：#320 是 coding/detail/evidence 线，不是 leader 产品设计主线。

#320 要求一个 probe 返回三大 business feature 和四层证据 verdict：CEO / Coder / Machine-readable / LLM-readable raw；它还提到 `docs/BUSINESS-FEATURES.md`、README 三大业务特性、`CLAUDE.md`/`AGENTS.md` canned-answer rule、grep anchors、CHANGELOG 等。citeturn148789view4

它应该给每个业务功能提供证明：

```txt
CEO:
  这个功能解决什么业务问题

Coder:
  哪些文件 / hooks / commands / routes 实现它

Machine-readable:
  JSON / SQL / CLI --json / DB schema 能证明它

LLM-readable raw:
  docs / logs / raw artifacts / canned answer anchors
```

但它不能反过来规定：

```txt
#308 必须怎么设计
#371 必须从 prompt 生成
#372 必须实时后台采集
```

#320 的位置是：

```txt
after design:
  add evidence anchors
  add canned answer
  add docs
  add --json / grep anchors
```

不是：

```txt
before design:
  force product shape
```
